# Payments write guard v1 (PROPOSED: not installed)

**Status: PREPARED, NOT APPROVED. Nothing here has run in production.** Tested only on the private
local Postgres 17 (127.0.0.1:55482, clones of the production-order baseline `rr_tpl`).

## Problem

RLS "Managers manage payments" (ALL) lets the Owner and every Manager change any payment row directly
through the API with their own session: mark a charge paid, un-pay a Stripe-collected one, waive or
void it, rewrite its amount or balance. Release 2's audited server function (`changePaymentStatus`)
is the intended path, but the database does not enforce it, and a direct change leaves no audit trail.

## Fix

A BEFORE INSERT OR UPDATE row trigger on `public.payments`, active only when the session role is
`authenticated` or `anon`:

| Change from a user's own session | Result |
|---|---|
| UPDATE of any money field: `status`, `amount`, `balance_due`, `late_fees`, `late_fee_applied_through`, `paid_date`, `refunded_amount`, `refunded_at`, the Stripe ids, `attempt_count`, `last_attempt_at`, `notified_status`, `failure_reason` | Refused: `payments_money_fields_change_only_through_audited_server` (42501) |
| UPDATE of `notes`, `due_date`, `payment_method`, `type`, `reason` or the links | Allowed |
| INSERT of a charge that starts owed (`upcoming`/`current`/… open status, no paid date, no refund, balance ≤ amount, no Stripe ids, no attempt state) | Allowed (Add Payment) |
| INSERT of anything else (paid, refunded, waived, void, pending, Stripe-linked) | Refused: `payments_new_charge_must_start_owed` |

These are unaffected:
- `service_role`: the audited staff actions, Charge Card / Pay Now collection, the Stripe webhook and the late-fee cron.
- SECURITY DEFINER functions owned by the database owner, such as `apply_payment_refund`.
- FK actions, which run as the table owner.
- The database owner itself, through approved SQL.

No policy, grant or row changes.

The install request:
- refuses any target other than the pinned production project;
- checks the inner checksum and takes advisory lock 7310405;
- refuses on journal drift, 0031 drift, a replay or a partial install;
- fingerprints `payments` (excluding its own trigger) and counts its rows before and after;
- verifies the function body hash and the trigger (tgtype 23, enabled);
- writes the evidence row `payments_write_guard_v1`.

The rollback mirrors it, keeps the install evidence, and writes `payments_write_guard_v1_rollback`.

The preflight (14 rows) also requires:
- no SECURITY INVOKER function that writes `payments`;
- triggers on `payments` = `payments_updated_at`, optionally plus `zz_payments_delete_guard`.

## Installation order (separate production approval; not authorized now)

1. **Release 2 must be live first.** Release 1's Payments screen still changes status directly. With this guard installed, its Mark as Paid, Waive and status menu would fail closed (error, no change). Release 2 moves them to the audited server function.
2. The payments delete guard, if approved, goes first. Its reviewed preflight expects `payments_updated_at` as the only trigger. This package's preflight accepts both states.
3. Run `preflight-readonly.sql` read-only. Every row must be ok.
4. Submit `request-payments-write-guard.sql` once, exact bytes, through `query_database`. No retry.
5. Run `verify-after-readonly.sql` read-only right after. Every row must be ok. It fingerprints `payments` as installed, so a later change such as installing the delete guard afterwards makes it differ.

Rollback: `request-rollback-payments-write-guard.sql`, once, under its own approval. No app change needed.

## Local proof

`node scripts/payments-write-guard.db.test.mjs`: **16/16**.

- **Before the guard:** a Manager and the Owner can mark paid and un-pay directly (the exposure).
- **Package mechanics:**
  - The preflight is all ok except the two local target rows.
  - The real request and the trailer pass the guard and then refuse the foreign target.
  - Tampering and trailing SQL are refused.
  - An injected failure rolls everything back.
  - A local copy installs, verify-after is all ok, and a replay is refused.
- **Roles:**
  - Manager and Owner: all 13 direct money-field changes are refused, including un-paying a paid row. Notes, due date, method and type stay editable, and an unchanged value is allowed.
  - Add Payment: an owed charge is allowed; 9 kinds of non-owed insert are refused.
  - Coordinator and driver: RLS gives no write, so nothing changes and inserts are refused.
  - Anon: no grant.
- **Paths that keep working:**
  - `service_role`: the collection claim, a webhook paid update, the notice claim, Charge Card's insert, and a staff waive.
  - `apply_payment_refund` (SECURITY DEFINER) still applies refunds.
  - A parent delete still sets the link to null.
- **Rollback:**
  - The real rollback request refuses the foreign target.
  - A local rollback removes exactly its two objects, keeps the evidence and refuses a replay.
  - The exposure returns, as expected.
- **Coexistence:** works with the payments delete guard in both install orders, and each rolls back without touching the other.

## Limits

- The database owner (approved SQL, the Supabase dashboard's table and SQL editors) can still change anything. Keep that access to the Owner.
- `notes` stays editable, so the Release 2 reason text appended to `notes` can be edited. The immutable record is the `audit_log` row written by the server function.
