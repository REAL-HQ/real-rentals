# Payments delete guard v1 (PROPOSED: not installed)

**Status: PREPARED, NOT APPROVED. Nothing here has run in production.** Tested only on the private
local Postgres 17 (127.0.0.1:55482, a clone of the production-order baseline `rr_tpl`).

**Problem:**
- RLS "Managers manage payments" (ALL) lets any Manager delete a payment row.
- No trigger prevents it.
- The Payments screen offered **Delete**.

Payment rows are financial history: a charge is written before collection, revenue is `net_collected`, and refunds are recorded per row.

**Fix:**

| Part | Status | Change |
|---|---|---|
| App | `fix/payment-delete-protection` | Payments → **Void (Entered In Error)** replaces Delete. It asks for confirmation showing the amount removed from what the driver owes, requires a reason (saved in `notes`), keeps `amount` and `balance_due`, and is offered only on unpaid, not-in-flight rows (not paid, refunded, waived, void or pending). No source file deletes payments (`scripts/payment-delete-ui.test.mjs`, in `npm test`). |
| Database | This package; not installed | A BEFORE DELETE row trigger refusing deletes from `authenticated`, `anon` and `service_role` (`payments_are_financial_history_void_instead`, SQLSTATE 42501). |

The two parts are independent. Install the app part first; the database part follows under its own approval.

## What the database part changes

| Changes | Untouched (checked inside the package) |
|---|---|
| `private.payments_delete_guard()`: SECURITY INVOKER, `search_path=''`, no API role may execute it | Every `payments` row (count before = after) |
| `zz_payments_delete_guard` BEFORE DELETE FOR EACH ROW on `public.payments` | `payments` owner, RLS flags, ACL, columns, other triggers and policies (fingerprint before = after) |
| One `audit_log` evidence row `payments_delete_guard_v1` | Security 0031 policies, first 23 Drizzle receipts, receipt count |

- The database owner (approved SQL, migrations, SECURITY DEFINER functions owned by it) can still delete.
- Parent deletes still work: the payments FKs are `ON DELETE SET NULL`, so the payment is kept with its link cleared.

Each request = submission guard v3 (`scripts/sql-guard/gen-guard3.py`) + the exact package bytes. The package is one DO block that:
1. refuses any target other than project `yuyzdsnrbfhkmfzpvhwx` / system identifier `7642734024280108049` / database `postgres` / executor `postgres`;
2. checks the inner SQL checksum, takes advisory lock 7310404 and locks the Drizzle journal, `payments` and `audit_log`;
3. refuses on journal drift, 0031 drift, a replay (evidence row present) or a partial install;
4. runs the DDL, verifies the function body hash and the trigger (tgtype 11, enabled), re-checks the fingerprint, row count, 0031 and journal, and writes the evidence row.

The rollback request mirrors it: refuses unless the install evidence exists, no rollback evidence exists and the function body is unchanged; removes exactly the trigger and function; writes `payments_delete_guard_v1_rollback`. The install evidence row is kept.

## Installation order (separate production approval; not authorized now)

1. The financial-integrity app release (Void replaces Delete) is live and Owner-confirmed.
2. Run `preflight-readonly.sql` read-only. Every row must be ok (12 rows, including triggers = `payments_updated_at` only and FKs set-null only).
3. Submit `request-payments-delete-guard.sql` **once**, exact file contents, through `query_database` on project `8cf1f99e-71ad-4a93-a47c-bfbe833616d6`. No retry. If the response is ambiguous, inspect read-only and stop.
4. Run `verify-after-readonly.sql` read-only. Every row must be ok (6 rows).

**Rollback:** submit `request-rollback-payments-delete-guard.sql` once, under its own approval. App behaviour does not depend on the trigger, so a rollback needs no app change.

## Local proof

`node scripts/payments-delete-guard.db.test.mjs` (disposable Postgres on 127.0.0.1:55482): **17/17**.
- Artifacts match `SHA256SUMS`; the build reproduces them.
- Before the guard, a Manager can delete (today's exposure).
- Preflight: every row ok except the two local target rows.
- The real request plus the Management API trailer passes the guard and then refuses the foreign target, leaving nothing behind. A tampered request or extra trailing SQL is refused by the guard.
- An injected failure after the DDL rolls everything back.
- A local copy (target profile substituted) installs. Verify-after is all ok. A re-run is refused (`PDG_EVIDENCE_REPLAY`).
- Manager, server code (`service_role`, paid or unpaid rows) and anon are refused.
- Voiding still works and keeps `amount` and `balance_due`.
- Parent deletes keep the payment and clear the link. The database owner can still delete.
- The real rollback request refuses the foreign target. A local rollback removes exactly the trigger and function, keeps every row and both evidence rows, and refuses a replay.

## Residual (not changed here)

- `service_role` holds TRUNCATE on `payments` in the baseline. A row trigger does not fire on TRUNCATE. Neither PostgREST nor supabase-js can issue TRUNCATE, and the app never connects with SQL as `service_role`, so it is not reachable from the app. Revoking it is a grant change and needs its own approval.
- Waive (existing action) removes a balance with no reason or confirmation. Not changed here.
