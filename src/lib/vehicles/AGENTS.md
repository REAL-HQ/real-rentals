- Vehicle Readiness checklist: rules live in vehicleReadinessChecks (src/lib/vehicle-readiness.ts) returning ReadinessCheck[]; the UI only renders that shape, so a future server readiness function can replace the calculation without UI changes.
- Readiness classification: every ReadinessCheck carries a category (operational / compliance / listing) and readinessByCategory groups them. Grouping only — statuses, overallReadiness and the enforced gate (vehicle_rental_ready_missing: identity + valid VIN + positive rate) are unchanged, and a document is never a substitute for a date. A published photo still has no bearing on renting, which is why vehicleReadinessChecks no longer takes a photo count.
- Title facts are three, not one: documentOnFile (a scan, from the document slots), metadataRecorded (vehicles.title_on_file, set only when an Owner records details in vehicle_titles) and the title number/status themselves, which stay Owner-only. getVehicleProfile returns the first two as `title`, every tier sees the same answer, and a document on file never means a title is verified.
- Readiness Fix actions carry the vehicle id, and `id` is owned by the inspections tab in admin.tsx PARAM_OWNER — without that the router strips it back out and Start Inspection falls back to whichever vehicle sorts first. startInspection re-checks the vehicle server-side (exists, not archived).
- Save feedback: a save answers with what it DID, not "Saved". applySection returns saved / unchanged / rejected / ignored (vehicles.functions.ts) and the per-section drawers post `intended` — the fields the operator actually edited — because they post the whole record and would otherwise have every column reported back. A Manager's Owner-only title value is `rejected` with the reason and the drawer stays open; nothing changed is "No changes to save". applyImportDecisions answers the same way (applied / unchanged / needsConfirmation / rejected) and VehicleSuggestions reads those arrays — never the count out of the message sentence.
- Fleet-wide readiness: the Vehicles list grades every car in the current filter scope with readinessBand/readinessGaps (src/lib/vehicles-list.ts), which call rentalReadyItems and one published vehicle_media row — not a fourth definition of readiness, and not a gate. The chips count the SCOPE, never the page; the `ready` filter resolves to ids before range() so pagination stays correct, and `ready` is owned by the vehicles tab in admin.tsx PARAM_OWNER or the router strips it. One capped sweep (READINESS_SWEEP_MAX); past that readinessPartial is reported rather than a number that is only mostly true, and the real fix is the two rules as a filterable view (a migration).
- Add Vehicle, paperwork step: after a car is saved, AddVehicleDialog offers the SAME VehicleDocuments panel the profile's Paperwork tab uses — one uploader, one extraction pipeline, one review. Optional by construction: the vehicle already exists, Skip is a complete answer, and details read from a document still need accepting field by field.
