- Vehicle display text: descriptive fields (make/model/trim/color) are re-cased via src/lib/display-normalize.ts at write time; identifiers are never re-cased and raw extracted text stays in vehicle_field_provenance.
- Fleet counts: every Overview fleet number comes from src/lib/fleet-summary.ts — because separate status queries disagreed.
- Vehicle Defaults: new-vehicle pricing resolves only via src/lib/vehicle-defaults.ts (explicit → type default → Not Set), Owner-write + audited, copied at create, never retroactive or from documents — pricing must be a human-confirmed snapshot.
- Vehicle document presence: every "is X on file / how many documents" answer comes from src/lib/vehicle-doc-presence.ts (+ .server loader), which merges direct documents and document_vehicle_links by document id and maps document classes to slots; finance kinds are withheld from Coordinators server-side — because one-off slot checks made a linked Fleet Inbox PDF read "Not on file".
- Service evidence: one fleet_service_transactions row per real invoice (service-transaction.ts rules, service-ingest.server.ts I/O); Apply = one service record, ≤1 expense, ≤1 mileage; Coordinators get only the operational half and never priced originals (documents.evidence_class) — per-file proposals multiplied expenses and leaked costs.
- Phone/SMS consent: company phone only via Settings business_phone (src/lib/company*.ts); opt-in wording+version only from src/lib/sms-consent.ts, evidence stored server-side — must match carrier registration.
- Experience switcher (lib/experience.ts) is view-only: never changes roles/tokens; driver preview loads no driver data.
- Fleet Inbox: all fleet-file ingestion goes through src/lib/fleet-inbox.functions.ts (originals stored once in documents + private vehicle-docs, one→many via document_vehicle_links, proposals re-derived server-side from src/lib/fleet-inbox.ts rules at apply, finance facts only in Owner-only fleet_import_finance_facts → vehicle_finance); document reading goes through src/lib/document-reader.server.ts — because AI must only propose and never silently overwrite authoritative fleet data.
- Fleet Inbox analysis runs through one core (src/lib/fleet-inbox-core.server.ts analyzeItemCore) used by both the staff action and the background worker (/api/public/cron/fleet-inbox, fleet_inbox_jobs queue: DB-woken on enqueue, retry timer armed only while open jobs exist, lease single-flight, backoff, dead-letter, AI 402/403 pauses the queue) — so a file is analyzed once, never by a parallel path, and never inside the inbound webhook.
- Fleet Inbox financial documents (payments/receipts classes) are read by src/lib/financial-ingest.server.ts and judged by pure rules in src/lib/financial-docs.ts (money event, duplicates, payment↔invoice/expense correspondence, vehicle suggestions); results live on the import item and are Manager+ only — because this path only proposes and must never post expenses, assign vehicles or touch vehicle finance.
- Vehicle profile completion: suggestions come only from existing Fleet Inbox proposals via getVehicleSuggestions (exact VIN only; near-VIN/plate-only listed as possible matches without values) and are applied through applyImportDecisions with partial=true — so there is one apply path, blanks only, Owner-only fields refused server-side.
- Blank-only vehicle comparisons (suggestions and apply) must overlay Owner-only vehicle_titles via overlayTitles (fleet-inbox-core.server.ts) and load only the target vehicle — because vehicles.title_* is always blank and comparing against it would overwrite real titles.
- Safe Autofill: only src/lib/safe-autofill.ts rules + safe-autofill.server.ts I/O, run after buildItemProposals (no extra AI), Owner setting default Off, daily cap, error pauses, blank-only conditional writes with vehicle_autofill_events history + Owner undo that skips later manual edits — because automatic writes must be reversible and never touch sensitive or nonblank fields.
- Financial ledger (Step C1): every money fact lives in financial_transactions and changes only through the public.fin_* database functions (called via src/lib/financial-ledger.functions.ts as the signed-in user); posted rows are immutable (reverse/correct instead), invoices count only in accrual and payments only in cash, linked by financial_settlements; acquisition/financing rows are owner_only — because a ledger must never double-count, be edited in place, or be posted automatically.
- Deposits in the ledger: deposit_received is cash in + liability (never revenue); deposit_applied is basis "none" (no cash, no accrual; settles a charge via fin_settle); deposit_returned is cash out; applications/refunds must name deposit_source_id and fin_deposit_guard caps them at the posted deposit — because applying a held deposit must never count cash twice.
- Driver Payment/Deposit status: derive only via driver-payment-status.ts, served to list and profile by getDriverPayStatuses (driver-payment-status.functions.ts) from rentals + payments; resolved/void/waived/cancelled charges never count; applications.payment_status/deposit_status are legacy defaults ("current"/"not_paid") and must not be displayed.
- Waitlist: promotion only via public.promote_waitlist_entry (atomic, reuses existing applicant, keeps original signup date/source); Drivers 'Waitlist' is a display hold in application_waitlist_holds (append/close-only, one active per application, Manager+ via setWaitlistHold) that never changes applications.status; linked applications are closed, never deleted — because promotions duplicated profiles and deletes hit waitlist_promoted_application_id_fkey.
- Driver deletion: only via src/lib/driver-deletion.functions.ts → Owner-checked DB functions (soft_delete/restore/purge_application, set_legal_hold); direct DELETE on applications/waitlist is revoked for app roles, public.driver_deletion_blocker (active rental, unpaid payment, open toll) gates both delete steps, and Restore reopens the Waitlist hold with its original added_at; purge anonymizes a tombstone row, removes identity documents only and queues files in deletion_file_jobs — because raw deletes cascaded signed agreements and orphaned financial history.

- Email-to-Evidence: inbound email enters only via /api/public/inbound/email (svix-verified, fail-closed) → src/lib/inbound-email.server.ts, which preserves the email in inbound_emails and drops sniffed, hash-deduped attachments into a normal Fleet Inbox batch (source_channel='email'); classification, grouping and Review/Apply stay in Fleet Inbox — because email must never become a parallel or auto-applying pipeline.
- Portal identity: one auth user per verified email; passwordless code/link only via src/lib/portal-signin.server.ts (hashed, single-use, rate-limited, generic public answers; accounts created only after verification, flagged portal_verified so approval adopts them; links exactly one unambiguous application, else staff review; staff excluded); non-drivers see stage views via portal-access.functions.ts — because a typed email must never create an account or expose records.
- Identity conflicts (same phone, different email; ambiguous portal matches) live only in application_identity_reviews (server-written, staff-read via RLS, Manager+ resolve via identity-review.functions.ts, audited) — never in ai_flags, because re-scoring overwrote them.
- eSign delivery: email/SMS outcomes are recorded per channel on the agreement (sent/failed/not_attempted) via deliverSigningLink and never change document status; Retry Delivery = Resend and always rotates the token, because only the token hash is stored.
- eSign PDF access: completed PDFs reach browsers only as bytes from getAgreementPdf (caller RLS decides access, server downloads from the private bucket), saved via saveAgreementPdf; never hand out storage signed URLs, because browser filters block the storage host and paths leak.
- eSign templates: approved-template enforcement is on only when the Owner's audited esign_template_enforcement switch is on AND an approved version exists; company details come from Settings → Company via company-identity.server.ts — so the migration alone never blocks sending.

- Vehicle Readiness checklist: rules live in vehicleReadinessChecks (src/lib/vehicle-readiness.ts) returning ReadinessCheck[]; the UI only renders that shape, so a future server readiness function can replace the calculation without UI changes.
- Readiness classification: every ReadinessCheck carries a category (operational / compliance / listing) and readinessByCategory groups them. Grouping only — statuses, overallReadiness and the enforced gate (vehicle_rental_ready_missing: identity + valid VIN + positive rate) are unchanged, and a document is never a substitute for a date. A published photo still has no bearing on renting, which is why vehicleReadinessChecks no longer takes a photo count.
- Title facts are three, not one: documentOnFile (a scan, from the document slots), metadataRecorded (vehicles.title_on_file, set only when an Owner records details in vehicle_titles) and the title number/status themselves, which stay Owner-only. getVehicleProfile returns the first two as `title`, every tier sees the same answer, and a document on file never means a title is verified.
- Readiness Fix actions carry the vehicle id, and `id` is owned by the inspections tab in admin.tsx PARAM_OWNER — without that the router strips it back out and Start Inspection falls back to whichever vehicle sorts first. startInspection re-checks the vehicle server-side (exists, not archived).
- Agreement preparation: per-rental choices (authorized drivers, reservation fee, deposit) are validated structured input (src/lib/agreement-prep.ts) passed to previewAgreement/sendAgreement and folded into the fingerprinted merge data — never contract text, so Send still re-renders server-side and refuses on mismatch.
- Vehicle Profile uploads (source_channel vehicle_profile) go through Fleet Inbox with Safe Autofill skipped; fields change only via explicit Accept in VehicleSuggestions — one reader, one apply path.
- Staff-review channels: Safe Autofill is skipped for every channel in STAFF_REVIEW_CHANNELS (fleet-inbox.ts) — Vehicle Profile and Vehicle Photos today. Add a new staff-facing channel THERE, never by widening a comparison at the call site; an unlabelled batch still behaves like Fleet Inbox.
- Vehicle photo reading: ordinary photos enter the SAME Fleet Inbox pipeline via readVehiclePhoto (vehicle-photo-analysis.functions.ts) — a documents row pointing at the existing private vehicle-photos object (bytes are never copied), one item, the ordinary job queue, VehicleSuggestions, applyImportDecisions. Never a second extraction path.
- Photographs as evidence: isPhotoClass gates it. A photo may offer only what is visible on the car; PHOTO_NEVER_FIELDS refuses registration, insurance, title and finance in the shared rules (so the apply-time revalidation refuses them too), photo items file no finance facts, PHOTO_AUTH keeps photos below paperwork, only originals are read, and no photo-derived value is ever `safe` — every one needs an individual tick.
- Photo Reading cost control: reading a photograph is the only thing here that spends money, so it is Owner-gated and capped. Settings live in app_settings['photo_reading'] (src/lib/photo-reading.ts rules, .server.ts I/O), default Off; the daily counter moves by compare-and-swap on the row's `version`, never by counting rows, so two simultaneous Reads cannot both take the last slot. readVehiclePhoto reserves AFTER every validation and the duplicate check, and releases the slot if the work never reaches the queue. app_settings RLS is admin-only for every command, so the Owner boundary is the database's, not the UI's.
