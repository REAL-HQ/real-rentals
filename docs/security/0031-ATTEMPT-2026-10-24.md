## Cause

Lovable's migration tool is the **Drizzle migrator**, not `supabase/migrations`:
the rehearsal project has a drizzle ledger and no `supabase_migrations` schema, and a
fail-on-purpose probe there saw 23 drizzle rows mid-execution (the receipt is written
*after* the SQL). The migrator applies **every pending journal entry in one
transaction**. Production's `drizzle/migrations/meta/_journal.json` still lists
`0023_application_resume_atomic_security` (when 1792545492197, newer than the last
receipt 1792408979135), so it ran first inside the attempt, wrote receipt 24, and the
0031 pin at 23 refused. 0023's effects rolled back with everything else.

## Consequences for the approved plan

- The packet's route and receipts were wrong for this tool: a successful install
  writes a **drizzle** receipt (23 → 24) and **no** Supabase receipt (stays 105).
- While 0023 is pending in the journal, **any** Lovable migration also runs 0023.
- The tool offers no approval pause; the operation runs as soon as it is submitted.
- The agent re-types the SQL into the tool call. The inner checksum gate covers the
  policy SQL; the drizzle receipt hash (sha256 of the stored file) can prove the whole
  file was byte-identical after the fact.
