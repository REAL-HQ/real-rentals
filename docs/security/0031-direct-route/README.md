# Security 0031 — direct, guarded submission (proposal; nothing executed in production)

Prepared 2026-10-24. The approved package `../0031-package/0031_guarded_coordinator_containment.sql`
(`32c17aa76e5026c4f50a2179aab143baa5d05463743b1a0f366ab4339103494f`) is unchanged.
No production SQL, migration metadata or deployment was touched while preparing this.

## Answer: yes, a supported selective route exists

Lovable's `query_database` (MCP) is a supported Lovable capability. It runs SQL through
Supabase's Management API (`POST /v1/projects/:ref/database/query`, `application_name =
mgmt-api`) as `postgres`, and it does not involve Drizzle. The approved preflight already
read production's values through this channel on 2026-10-24
(`../0031-attempt-2026-10-24/preflight-result.json`): `current_user = session_user =
postgres`, `transaction_read_only = off`, and `supautils.policy_grants` names
`storage.objects`. Those are the package's own pins.

The package was designed for this. It is one `DO` statement. It needs **no** receipt: it
requires the Drizzle ledger to be exactly the 23 production receipts **before and after**
its DDL (`JOURNAL_DRIFT_OR_REPLAY`, `POST_JOURNAL_CHANGED`). Its record is the immutable
`audit_log` evidence row it writes itself.

| | Drizzle migration tool (failed 2026-10-24) | Direct guarded submission |
|---|---|---|
| Runs pending `0023` | yes, in the same transaction | **no**: Drizzle is not involved |
| Journal or metadata change | needs the `0023` deferral | **none** |
| Receipts | Drizzle 23 → 24 | **none**: Drizzle stays 23, Supabase stays 105 |
| Who types the SQL | the Lovable agent re-types it | Claude passes it, and an in-database guard checks it **before** anything runs |
| Approval pause | none | none (submission is execution) |

Migration history stays unambiguous. Both ledgers keep describing exactly the files they
ran, and no "reconciled" receipt is invented. The install is recorded in four places:
1. the package's `audit_log` row, which holds the SQL hash, executor, session and transaction id;
2. `pg_stat_statements`, the database's own record of the executed text;
3. the read-only before/after fingerprints;
4. this directory, committed with the results.

## Proof that the approved bytes are what runs (before execution, not only after)

`request.sql` (`0d0c67d8…77d`, 23,851 bytes) is `submission-guard.sql` (`6f1bf178…00a`,
1,362 bytes, generated by `gen-guard.py`) followed by the **unchanged** package bytes. The
guard is a separate statement in the same request. It reads `current_query()`, the text the
server actually received, and refuses unless all of the following hold:

- the request starts with the guard (`RRGUARD_TEXT_BEFORE`);
- the package follows the guard immediately, with nothing between them (`RRGUARD_TEXT_BETWEEN`);
- the package's header line appears exactly once (`RRGUARD_PACKAGE_MISSING`);
- the 22,489 bytes after it hash to `32c17aa7…494f` (`RRGUARD_BYTES_MISMATCH`);
- nothing follows except the Management API's own comment trailer (`RRGUARD_TRAILING_TEXT`).

The request runs as one transaction, so a guard refusal also undoes anything placed before it.

After a successful install, `verify-after-readonly.sql` must show `executed_text`
`{len 22487, sha 6cf64c7e2802f30a874bb0ed9750bf1c99f78e57d1defb78ceac96de8ff8f8cb}`. That is
the package minus its final `;\n`: the database's own record that exactly those bytes ran.

## Procedure (each production step requires the approval below)

1. Read-only: `../0031-preflight-readonly.sql` and `fingerprint-readonly.sql`. Every gate
   must equal the 2026-10-24 values (Drizzle 23, Supabase 105, catalog `c753236e…`,
   evidence rows 0). **Stop on any difference.**
2. One `query_database` call to project `8cf1f99e-71ad-4a93-a47c-bfbe833616d6` with exactly
   `request.sql`.
3. Read-only, regardless of the response: `verify-after-readonly.sql`, then
   `fingerprint-readonly.sql`. The fingerprint must equal the "before" one except
   `policies_total` +5, `storage_objects_policies` +1 and `audit_log_rows` +1;
   `policies_other_md5` must be unchanged.
4. Access tests from `../0031-installation-plan.md` §verification: Coordinator denied
   identity rows, documents and the four identity buckets; Owner and Manager unchanged.
5. Commit the results here.

## Recovery

| Outcome | Meaning | Action |
|---|---|---|
| `RRGUARD_*` | the guard refused; **nothing ran** (shown by test G) | run step 3 to confirm no change; do not resubmit without a new approval |
| A package gate (`TARGET_MISMATCH`, `JOURNAL_DRIFT_OR_REPLAY`, `SCHEMA_POLICY_GRANT_DRIFT`, `POST_*`, …) | one atomic statement, so everything rolled back | step 3 must show the before-fingerprint exactly; stop and report |
| No response or a timeout | unknown | **never resubmit blind.** Step 3 decides: 5 policies + 1 evidence row = installed; 0 + 0 = not installed; anything else cannot result from one atomic statement, so stop and report. An accidental second submission after success is refused by `PARTIAL_INSTALL` and `EXECUTION_EVIDENCE_REPLAY`. |
| Installed but an access test fails | the policies need to come out | the reviewed `DROP POLICY` rollback (`../0031-installation-plan.md`), as its own approved operation; the `audit_log` row stays, by design |
| Journal inconsistency | not possible from this route: no file, journal or receipt is written | — |

## 0023 — unchanged, and still a standing hazard

The direct route leaves `0023_application_resume_atomic_security` exactly as it is: pending
in the production journal. Its file and snapshot are untouched and no deferral is needed.
However:

- **Any** future Lovable migration, by anyone including the Lovable agent, applies `0023`
  first, in the same transaction, as on 2026-10-24.
- If that happens **before** 0031 is installed, the Drizzle ledger becomes 24 and the 0031
  package refuses (`JOURNAL_DRIFT_OR_REPLAY`). 0031 would then need a reseal and a new
  approval.

Install 0031 before any other Lovable migration runs, then decide `0023` as its own
operation.

The timestamp deferral (`../0031-0023-deferral.diff`, `../0031-EXECUTION-CORRECTION.md`) is
no longer needed and should not be applied. It remains documented only as the fallback if
the direct route is declined.
