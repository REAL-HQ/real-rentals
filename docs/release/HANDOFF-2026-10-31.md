## 5. Standing rules (from the Owner; all still in force)

- **Needs explicit Owner approval:**
  - publishing;
  - any production SQL (including read-only queries, when the Owner says "no SQL");
  - database migrations;
  - customer-data changes;
  - live Stripe operations (charges, subscriptions, refunds, imports);
  - permission changes;
  - turning on any disabled feature.
- **Submit once.** Every approved production submission is sent exactly once, with no automatic retries. If a result is ambiguous, inspect read-only and stop. A timeout or ambiguous payment response must never be retried with a new idempotency key.
- **Credentials:**
  - Never request, store or display Stripe secret keys or production service-role credentials.
  - Never add a generic privileged SQL endpoint.
- **No test transactions:** no test applications, payments or customer records in production. No production emails or SMS for testing.
- **Payment rows:** never delete them; void with a reason instead. Never activate autopay. Keep the insurance exception OFF.
- **Do not modify:**
  - Security 0031, S1 or the approved policies;
  - existing rollback branches or refs, or the frozen branches.
- **Do not install:** M2 Window 1/2 or proposed `0033_stripe_reconciliation`, without separate review and approval.
- **Drizzle 0023:** installed 2026-10-31 with Owner approval (see §11). Turning resume on, publishing, a rollback, or setting `APPLICATION_RESUME_ATOMIC_ENABLED` each need separate approval.
- **Visual checks:** if a hosted Preview can't be reached, mark the visual checks UNVERIFIED.

## 6. How production SQL has been done (only with approval)

- Through Lovable `query_database` on the project above.
- **Read-only queries** start with `SET TRANSACTION READ ONLY;` and return aggregates, hashes or names, never customer row data.
- **Installs** are guarded packages (`proposed/<name>/request-*.sql`). Each one:
  - checks its own bytes;
  - is pinned to the system identifier;
  - checks the journal and 0031 hashes;
  - writes one `audit_log` evidence row.
- An install is sent byte-for-byte, once. Success returns `{"rows":[]}`. A preflight comes before it and a verify-after comes after it, both read-only.

## 8. Known limits and accepted items

- **Only the Owner can Charge Card.**
- **End Rental closes the driver's application.** A returning driver needs it reopened.
- **Managers could delete *closed* rentals** through RLS. The procedure is never to delete rentals.
- **The payment guards don't cover everyone.** They don't apply to the database owner or the Lovable platform role `sandbox_exec`. Keep Lovable workspace edit access to trusted staff.
- **TRUNCATE on `payments`** is still granted to the API roles. PostgREST cannot issue it; a grant review is deferred.
- **Autopay code is unsafe:** subscription creation, End Rental and Stop Autopay all have problems. Don't enable it without a reviewed fix.
- **PostgREST 14.5 behaviour of one webhook filter** (`.or()` + select) is untested against production. It is covered by state guards.
