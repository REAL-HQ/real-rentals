- eSign: all signing/voiding/archiving goes through src/lib/esign.server.ts (atomic esign_claim/esign_void DB functions, PDF + SHA-256 archive with visible archive_status); rental agreements are a consumer — never add a parallel signing path.
- Rentals: start/end only via activate_rental_tx / end_rental_tx (called from rentals.functions.ts); triggers guard_rental_lifecycle and guard_vehicle_rented_status refuse any other path, because split writes left rentals and vehicles disagreeing.
- Payments: a payments row is a charge written before collection (payment-collection.server.ts only moves status); revenue = net_collected; refunds only via apply_payment_refund; the webhook never un-pays and claims notices via notified_status — no double charges/emails.
- Agreements: buildMergeData's blockers are the single readiness gate for preview, send, approval auto-send and resend; every rendered contract field must be real data (real vehicles.vin, never record ids).
- Agreement preview/send: prepareAgreement is the one generation step; staff Send carries the preview's SHA-256 fingerprint and the server re-renders and refuses on mismatch; no browser-supplied contract text — so the driver gets exactly what was reviewed and wording changes only via Owner templates.
- Vehicle photos: the vehicle-photos bucket is private (staff-only storage policies); the public site gets listing photos only via /api/public/vehicle-photos/*, which serves a path only if a published vehicle_media row names it, and staff galleries download bytes via loadStaffPhoto — because unpublished originals and AI retouches must never be publicly reachable.
- Vehicle sharing: Manager/Owner-only packages go through vehicle-share.functions.ts; the first quick package contains only approved AI enhancements, automatic insurance packages use published lead/listing order plus a VIN/registration snapshot, and manual packages allow originals and approved derivatives. Only SHA-256 token hashes and reviewed snapshots are stored in staff-only app_settings. Top-level share routes validate token lookup, expiry, revocation and media membership before streaming no-store bytes; canonical email/SMS only — private originals never become listing photos. Recipient URLs resolve only to the public website, never localhost or staff Preview hosts, so recipients can open emailed, texted and copied links.
- Fleet Inbox: all fleet-file ingestion, analysis and financial-doc rules live in src/lib (see src/lib/AGENTS.md); AI only proposes, never overwrites fleet data.
- Vehicle readiness: status, Rental Ready (public.vehicle_rental_ready_missing: identity + valid VIN + positive rate), Listing Ready (+ explicitly published photo, vehicle_listing_ready_missing) and profile are separate; vehicle-readiness.ts only mirrors them; unknown rate/deposit stays null; only a human makes a car Available — invented values corrupt pricing.
- Rental activation overrides: overriding soft blockers (e.g. no passed pre-delivery inspection) requires a written reason, recorded with blockers, actor, driver, vehicle and time in the immutable audit_log.
- Unit numbers: assigned only by the vehicles_assign_unit_number insert trigger from vehicle_unit_seq ; creation paths leave it blank unless a human typed one — because client max+1 suggestions collided.
- UI casing: labels/titles/tabs/menus are Title Case in the strings, never CSS text-transform — it corrupts eSign/VIN/GPS.
- Account presentation: format the existing session name and avatar through display-normalize.ts only; never write account data to correct display — presentation changes must not alter identity or access.
- Lead Priorities presentation: opt into neutral shared status/readiness styling without changing their default appearance or workflow, so dashboard redesigns never restyle other screens or alter classification.
- Maintenance: service writes only via maintenance.server.ts (one linked expense = net paid); mileage only in append-only odometer_readings (rental pickup/return via the rental tx, reusing inspection readings), current_odometer trigger-derived — no double counts.
- Uploads: new upload UI uses components/FileUploader.tsx (validate only; caller keeps its storage/pipeline); FileDropBridge covers legacy inputs; file-upload-guard test blocks new raw inputs — so drop = Browse.
- Owner-only finance: acquisition/lender/lien/payoff data (vehicle_finance, fleet_import_finance_facts, ownership-finance documents via private.is_ownership_finance_kind) is gated by private.is_owner() in RLS/storage and requireOwner/actor.tier==='owner' in server functions; Managers keep operating costs — because UI hiding is not a boundary. The Experience selector only changes layout, never access.
- Driver Preview: staff view a driver only via portal reads carrying previewDriverId, checked in driver-preview.server.ts (Manager+, real driver, audited); driver write actions call refuseStaffPortalWrite; no driver tokens ever — so preview can never act as the driver.
- Vehicle titles: title_number/title_status live only in Owner-only public.vehicle_titles (vehicles columns deprecated; a trigger diverts writes); staff see vehicles.title_on_file — because staff-readable vehicles rows leaked title identifiers.
- Photo enhancement: on-device only (photo-enhance.worker.ts, model loaded on request); results are review-pending ai_enhanced rows and a DB trigger blocks publishing until approved — no paid providers, no unapproved listings.
- Back-office sticky: chrome locked once in admin.tsx; pages opt filter rows in via `admin-sticky-bar` (styles.css) — no per-page sticky code.
- Overview summary details: use one shared expansion state and existing authorized responses; service previews deduplicate by vehicle and prioritize maintenance status — so expansion cannot change reporting, access, or service classification.
- Staff vehicle pickers default to shared thumbnail-first columns using existing staff media reads and confirmed-original thumbnail selection; keep option values, filtering and search unchanged — so uniform presentation cannot alter assignment or permissions.
- Driver profiles show one actionable server-readiness checklist in NextStepCard via embedded ActivationRequirementList; blocker actions reuse the same rows, insurance file/review shares one displayed row, and separate readiness insights stay under Review Notes. Grouped file fields share DriverDocumentUploadDialog category choices and independent staged FileUploader queues through use-driver-document-upload (the Documents vault sequence), preserving categories and permanent-agreement guards. Upload dialogs portal outside profile chrome and isolate Escape from activation. Circles open existing workflows; readiness remains server-derived, and uploads never verify insurance, sign agreements or activate renters.
- Quick phone-call completion uses existing driver_screenings interview metadata through quick-call.functions.ts: staff roles and reads/writes remain caller-RLS scoped, append an audit request before a conditional write, preserve answers/stage/negative findings, and return final audit failures visibly; it cannot approve or activate.
- Checklist evidence preparation uses checklist-evidence.ts for pure scoped attestations/projections and mock-only exception assessment; CHECKLIST_EVIDENCE_ENABLED stays false and its authenticated server seams always refuse persistence until an approved durable/atomic package is installed. Never feed mock eligibility into decideActivation, use local storage as saved evidence, or bypass the checked rental transaction—because checkbox color is not verification or authorization.
- Driver lifecycle presentation uses driver-lifecycle.ts with authorized completion facts; pickup-plan.ts and the unmounted plan/handoff/portal views are isolated drafts with live capabilities false, because a reviewed snapshot or mock diagnostic cannot authorize sending, saving or starting a rental.
- eSign tests run only against the disposable harness (scripts/esign-harness: throwaway Postgres + PostgREST + in-memory storage, outbound network refused, email/SMS capture-only) — never against the shared backend.

- Agreement templates: each agreement family has its own key, version history and fingerprint (src/lib/agreement-library.ts); prepareAgreement takes an optional templateKey, adds it to the fingerprint, and refuses Send for any family version not Owner-approved — so insurance and no-insurance wording never mix and drafts can't be sent.
